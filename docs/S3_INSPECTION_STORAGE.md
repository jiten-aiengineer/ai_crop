# Crop Life AI — Private S3 Inspection Storage

## What this release adds

Each submitted inspection now has one UUID generated by the server. The same
UUID is used for the Gemini assessment, private S3 image keys, PostgreSQL
inspection data, product-match records, and future Qwen comparison work.

```
browser
  -> Crop Life AI server
       -> private S3 (submitted, optimised crop photos)
       -> Gemini (immediate diagnosis)
       -> internal FastAPI endpoint (PostgreSQL metadata and results)
```

The browser never talks to S3 and is never given an S3 URL. The AWS SDK is used
only by `app/api/inspect/route.ts` in the Node.js server runtime.

## Private object layout

S3 keys contain no farmer, employee, email, phone, or other personal data.

```
inspections/YYYY/MM/DD/<inspection-uuid>/image-01.jpg
inspections/YYYY/MM/DD/<inspection-uuid>/image-02.png
```

Images are stored with their real submitted MIME type. The current browser
workflow reduces compatible photos before submission for speed, so the archive
contains the exact optimised image sent to Gemini—not an unseen second copy of
the original camera file.

## Required EC2 `.env` values

Set these in `/home/ubuntu/apps/ai_crop/.env`. Do not add AWS access keys or
secrets anywhere in the repository or environment file.

```env
AWS_REGION=us-east-1
S3_BUCKET_NAME=crop-life-ai-data
S3_INSPECTIONS_PREFIX=inspections
INSPECTION_PERSISTENCE_URL=http://127.0.0.1:8000/api/v1/inspections/persist
INSPECTION_PERSISTENCE_TOKEN=<one-long-random-internal-token>
```

`INSPECTION_PERSISTENCE_TOKEN` is an internal app-to-app token. It is not an
AWS credential. The frontend service reads it from the systemd environment
file, and Docker Compose passes the same value only to the private FastAPI
container. Keep the value out of Git and out of client-side variables.

The app creates `new S3Client({ region })` without a `credentials` setting.
On the EC2 instance, authentication therefore comes from `CropLifeAIAppRole`
and its short-lived IAM role credentials.

Do not set these archive variables in Vercel: Vercel has no attachment to the
EC2 IAM role and must not receive AWS keys. The Vercel app continues to return
the normal Gemini result when archive configuration is absent; the private image
archive is enabled only on the AWS-hosted app server.

## Database records

Migration `003_s3_inspection_persistence.sql` adds:

- inspection storage status and partial-upload failure details;
- S3 bucket and image order on `inspection_images`;
- `ai_provider_results` for Gemini today and Qwen/CLSL models later;
- an idempotency index for primary AI predictions;
- nullable `employee_id` for the unauthenticated web pilot, avoiding false
  attribution of every farmer inspection to the administrator.

Successful S3 uploads create one `inspection_images` row per object. Gemini
results are saved to both provider-generic audit data and the structured
`ai_predictions` table. CLSL catalogue-only recommendations are saved in
`inspection_recommendations`.

Training consent remains false by default. Private retention for inspection
history is not consent for model training; expert review remains required before
an image can become a verified training record.

## Controlled failure behaviour

| Situation | Behaviour |
| --- | --- |
| Gemini and S3 succeed | Full diagnosis, image records, provider result, and CLSL matches are stored. |
| Gemini fails, S3 succeeds | Images and a failed provider record are stored for later retry; the farmer gets a controlled AI error. |
| Gemini succeeds, S3 fails | Diagnosis still returns, but the API marks storage failed and the app visibly tells the user the archive needs retrying. |
| Some images fail | Successful S3 objects and rows are retained; failed image order numbers are recorded on the inspection. |
| Database persistence fails | Diagnosis still returns, but the app visibly states that the secure inspection record needs retrying. |

No S3 failure is reported as a successful archive.

## Production deployment and smoke test

After setting the EC2 environment values, deploy the exact committed source:

```bash
cd /home/ubuntu/apps/ai_crop
git pull origin main
npm ci
npm run build
docker compose up -d --build api
sudo systemctl restart crop-life-ai.service
```

Then upload one crop image in the AWS-hosted app. Confirm a corresponding key
exists in `crop-life-ai-data/inspections/` and run this read-only database
check on EC2:

```bash
docker compose exec -T db psql -U crop_life -d crop_life_ai -c "
SELECT i.id, i.status, i.image_storage_status, count(ii.id) AS stored_images
FROM inspections i
LEFT JOIN inspection_images ii ON ii.inspection_id = i.id
GROUP BY i.id, i.status, i.image_storage_status
ORDER BY max(i.created_at) DESC
LIMIT 10;"
```

Once the smoke test proves the restricted policy works, detach
`AmazonS3FullAccess` from the EC2 role and leave only the bucket-scoped policy.
The bucket must remain private with Block Public Access enabled.
